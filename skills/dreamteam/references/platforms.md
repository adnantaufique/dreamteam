# Dreamteam — Platforms (per-CLI tool / dispatch / model-tier map)

Dreamteam runs on **Claude Code**, **Codex CLI**, **Gemini CLI**, **CodeWhale**, **OpenCode**, and **Cursor**. The loop, gate, and Caster are CLI-agnostic; only three things resolve per platform — **tool names**, **subagent dispatch**, and **the host resolution of each abstract tier**. This file is the source of truth for all six. Default `--platform auto` (detect the host); `--platform claude|codex|gemini|codewhale|opencode|cursor` overrides.

## Tool-name map
The skill is authored in Claude Code tool names; on other CLIs read them as:

| dreamteam (Claude Code) | Gemini CLI | Codex CLI | CodeWhale | OpenCode | Cursor |
|---|---|---|---|---|---|
| Read / Write / Edit | read_file / write_file / replace | per `references/codex-tools.md` (superpowers) | native file read/write/edit (Claude-Code-style) | `read` / `write` / `edit` (native, Claude-Code-aligned) | native Read-files / Edit-files tools |
| Bash / Grep / Glob | run_shell_command / grep_search / glob | per `references/codex-tools.md` | native shell + search | `bash` / `grep` / `glob` (+ `list`) | Run-shell-commands (terminal) / file-and-folder search (+ semantic search) |
| Agent tool (dispatch subagent) | `@generalist` / `@code-reviewer` (named agents) | custom agent / spawn | a CodeWhale subagent | the `task` tool / `@<agent>` (native subagent) | a Cursor subagent via the `Task` tool (`/<agent>` or auto-delegation) |
| Skill / WebSearch / WebFetch | activate_skill / google_web_search / web_fetch | per `references/codex-tools.md` | `/skills` + MCP-provided web tools | native `skill` tool / native `websearch` (Exa-powered, off by default: needs the OpenCode provider or `OPENCODE_ENABLE_EXA`) / native `webfetch` | native Agent Skills (auto-matched on `description`) / `Web` search / `Browser` |

> The Codex column defers to `references/codex-tools.md`, which ships with the **superpowers** plugin (a REQUIRED compose, see `SKILL.md`) — install superpowers to resolve those tool names.

**MCP servers are host-level and exist on all six CLIs** — the cast-time MCP inventory (`references/caster.md`) resolves per the **host's own MCP config** (which servers are actually connected), never assumed from this map or from memory.

## Dispatch resolver
Dispatch a "**`<role>` at tier `<T>`**" resolves to:
- **Claude Code:** the Agent tool — `subagent_type=<agent>`, `model=<resolved>`.
- **Gemini:** `@<agent-or-generalist>` carrying the role prompt, with frontmatter `model: <resolved>`.
- **Codex:** a custom agent with `model=<resolved>` (+ optional `model_reasoning_effort`).
- **CodeWhale:** a CodeWhale subagent carrying the role prompt; model selected via `~/.codewhale/config.toml` (`[providers.<id>] model=<resolved>`), the `--provider` flag / `CODEWHALE_MODEL` env, or its auto-mode.
- **OpenCode:** a native subagent — markdown in OpenCode's agents dir (`~/.config/opencode/agents/<agent>.md`, or project `.opencode/agents/`) or JSON under `agent` in `opencode.json` — with `mode: subagent` + `model: <provider>/<resolved>`; dispatched via the native `task` tool or `@<agent>`. The model is resolved from the user's **configured provider** (OpenCode is bring-your-own-provider; see §"Abstract tier → host resolution"). dreamteam itself loads as a native Agent Skill via the `skill` tool — no AGENTS.md downgrade needed.
- **Cursor:** a native Cursor subagent — markdown + YAML frontmatter in `~/.cursor/agents/` (or project `.cursor/agents/`; `.claude/agents/` is read for compatibility) with `model: <resolved>` (a concrete picker ID, or `inherit`) and `is_background: true` — dispatched via the `Task` tool (parallel = multiple Task calls in one message), an explicit `/<agent>`, or auto-delegation off the subagent's `description`; subagents run in the editor, the CLI (`agent`, formerly `cursor-agent`; print mode `agent -p`), and Cloud Agents. Cursor's native nesting cap binds one level **below** a dreamteam leaf — since Cursor 2.5 a direct subagent **CAN** launch child subagents; only a subagent's subagent can't spawn further — a bound on runaway depth, **NOT** depth-1 enforcement: on Cursor the depth-1 invariant rests on the **prose leaf firewall** (the identity firewall, `SKILL.md` §Resilience + the leaf-firewall dispatch brief, `references/caster.md`), exactly as on the other non-Claude-Code platforms.
- **Execution mode is always background.** Dispatch the role via the host CLI's background/async form (on Claude Code: the Agent tool's background dispatch / `run_in_background`), never a foreground inline call. The **Workflow tool is Claude-Code-only**: on Claude Code the conductor offers a one-time per-session choice (background subagents [default] | Workflow, per `loop.md`); on Gemini / Codex / CodeWhale / OpenCode / Cursor there is no Workflow tool → background subagents, no prompt (on Cursor that resolves to native `is_background` subagents). The Workflow tool additionally exposes a **live run-level token budget** the conductor honors **when the session carries a user token target** (per `run_policy`'s budget-aware scaling, `references/caster.md`) — Claude-Code-Workflow-only; no equivalent exists on the other CLIs or in background mode. The `--execution` flag pre-sets that choice (`loop.md`): `--execution workflow` is **Claude-Code-only** — on Codex / Gemini / CodeWhale / OpenCode / Cursor it is rejected with a note and falls back to background subagents; `--execution background` is valid everywhere. **OpenCode caveat:** OpenCode's native `task` dispatch is **synchronous/modal** (blocking) in core, so "background" here means *dispatched via the `task` tool / `@<agent>` rather than the Workflow tool* — not non-blocking-in-chat; the conductor still awaits each result before gating, so the dispatch→await→gate→integrate contract holds either way. True non-blocking background is available only via a community plugin.

Parallel workstreams use each CLI's own parallel dispatch. Producers that **mutate files** still get an isolated workspace per `superpowers:using-git-worktrees` (CLI-agnostic).

## Abstract tier → host resolution (source of truth)
The rubric, profiles, and escalation name the **abstract** tiers — **cheap → standard → capable → max** — and this section resolves them **per host, at cast time**. It deliberately records **NO versioned model IDs as facts**: vendor lineups churn and a pinned ID rots silently, while family names and host-config rungs survive — this section's job was never to be a model database but to answer *"what does `capable` dispatch on THIS host, today?"*, and **the host always knows** (or the platform's official models doc, where the host surface doesn't enumerate the lineup). Per platform, one rule names (a) **WHERE the current lineup lives** — resolve there, never from memory — and (b) **HOW the four rungs map onto the host's own signals** (price order, family tiers, `small_model`-vs-`model`, picker groups). A rung-boundary judgment call (which of the host's models is the `standard` rung today) is resolved **at cast time and DECLARED via the existing manifest print** — `SKILL.md` spine step 1 already shows each pick's abstract tier → resolved concrete model — **no new mechanism**. And one rule the escalation ladder inherits: where a platform's `capable` and `max` rungs **currently coincide** (the top rung adds nothing on this host today), escalation to `max` is a **declared no-op** — flagged in the report per the tier-unavailable pattern (`loop.md` §"Model tier + escalation") — **never a silent same-model retry**.

| Platform | WHERE the current lineup lives | HOW the four rungs map onto the host's signals |
|---|---|---|
| **Claude Code** | the harness's own **family aliases** — the subagent / Agent-tool `model` field accepts `haiku`, `sonnet`, `opus`, `fable` (plus a full model ID or `inherit`), each alias tracking its family's current generation | the aliases ARE the rungs: cheap→`haiku` · standard→`sonnet` · capable→`opus` · max→`fable` |
| **Codex** | the **official models doc** (developers.openai.com/codex/models → learn.chatgpt.com/docs/models) for the lineup; `model` in `~/.codex/config.toml` **sets** the pick (plus `model_reasoning_effort`); the `/model` picker is a convenience where functional | the current family's price/capability order: cheap→its fast-and-affordable variant · standard→its balanced variant · capable→its flagship · max→its flagship + a raised `model_reasoning_effort` |
| **Gemini** | the CLI's **model config** — `model.name` in `settings.json` / `--model` / `GEMINI_MODEL` — plus the API's `thinking_level` | the Gemini **family tiers**: cheap→flash-lite · standard→flash · capable→pro · max→pro at its top `thinking_level` — as of 2026-07 `high`, the documented default, so capable and max **currently coincide** (a declared no-op per the intro) |
| **CodeWhale** | **`~/.codewhale/config.toml`** (`[providers.<id>] model=`) + the configured provider's own model docs (DeepSeek-first by default) | the provider's price order: cheap+standard→its flash/light-class model · capable→its pro-class model · max→its pro-class model + thinking mode |
| **OpenCode** | **`opencode.json`** — `model` (the main rungs) + native `small_model` (the cheap rung), IDs in `provider/model` form; the configured provider's lineup via models.dev | the **configured provider's** rungs: cheap→`small_model` / its mini · standard→its standard · capable→its large · max→its top reasoning model (+ effort where the provider exposes it) |
| **Cursor** | the **model picker** the user's plan actually offers (cursor.com/docs/models) | the picker's rungs: cheap→its mini/flash group · standard→its standard group · capable→its frontier group · max→its top reasoning model (`-high` reasoning-effort variants are separate picker IDs, resolved like any tier) |

- **Effort dial.** Codex exposes `model_reasoning_effort`; on Claude Code, **Workflow-mode `agent()` exposes an `effort` option** — the Agent tool (background-subagent dispatch) has no per-dispatch effort parameter, and its absence is fine, never an error. The dial is an extra lever **on top of** the tier, never a substitute for it — and **downward-only at dispatch**: where the table's `max` rung *is* capable + high effort, raising effort on a `capable` role lands on `max` (the escalation ladder's top — escalation or explicit override, never a casual dispatch-time raise); per-role guidance (which roles may run low, which never drop below the platform default) lives in the tier rubric (`references/caster.md` §"Model tier").
- **CodeWhale** is multi-provider: tiers map onto whichever provider `~/.codewhale/config.toml` names (DeepSeek-first by default; Anthropic/OpenAI/MiMo likewise), or CodeWhale's auto-mode picks the model + thinking level per turn. On the DeepSeek default, cheap and standard share the flash-class model; capable and max resolve to the pro-class, max adding thinking mode. Confirm exact IDs in `~/.codewhale/config.toml` / CodeWhale's `docs/PROVIDERS.md`.
- **OpenCode is provider-agnostic — never pinned.** OpenCode is bring-your-own-provider (75+ providers via models.dev), so each tier is the corresponding rung from whatever provider the user configured in `opencode.json` (`model` for the main rungs, native `small_model` for the cheap rung). Model IDs use OpenCode's `provider/model` form. Confirm the active provider's IDs against `opencode.json` + models.dev.
- **Cursor is never pinned either — the rung is the model picker's.** Cursor selects models per request from its picker (frontier models from OpenAI, Anthropic, Google, xAI + Cursor's own `composer` line), plus **automatic routing modes** of its own (currently `Auto Cost` / `Auto Balance` / `Auto Intelligence` — cursor.com/docs/models); resolve each tier to the corresponding rung of the models the user's plan/picker actually offers. Cursor exposes reasoning effort as separate `-high` **model variants** — a model ID resolved like any tier, NOT a dispatch-time dial. In a subagent the frontmatter `model:` takes the concrete ID (or `inherit`); in the CLI, `--model <id>`. Confirm live IDs against Cursor's model list (cursor.com/docs/models) — the picker's lineup moves faster than any file.
- **Dated examples (illustrative only — never load-bearing; the host's own list always wins).** As of **2026-07**: Codex's lineup is the GPT-5.6 family — `gpt-5.6-luna` (fast/affordable) · `gpt-5.6-terra` (balanced) · `gpt-5.6-sol` (flagship; a raised `model_reasoning_effort` on top for max), the `*-codex` line deprecated as user-selectable; DeepSeek (CodeWhale's default provider) offers `deepseek-v4-flash` / `deepseek-v4-pro` with thinking mode default-on — the old `deepseek-chat` / `deepseek-reasoner` endpoints are discontinued; an OpenCode cheap rung looks like `small_model: "anthropic/claude-haiku-4-5"`; a Cursor `-high` variant looks like `gpt-5.6-sol-high`. Claude and Gemini need no example — their rungs are the host's own family names.
- **Back-compat:** the resolver also accepts F1's Claude reference names — `haiku→cheap`, `sonnet→standard`, `opus→capable`, `fable→max` — so any pre-F3 manifest or `--roster` carrying a concrete Claude tier still resolves on every platform.
- **Capacity auto-detection resolves per host** (`references/caster.md` §"Capacity profile"): `--capacity auto` reads the **conducting model's own tier** — mapped against this table — as the plan proxy; **tier dispatchability** (an abstract tier that does **not** resolve to a dispatchable model on this host/plan) is a separate signal, informing the `low` row's best-available floor *resolution* and the once-only mid-run surprise downgrade — not what `auto` reads.

## Per-CLI install
- **Claude Code** → `install.ps1` / `install.sh` → `~/.claude/skills/dreamteam`.
- **Gemini** → `gemini-extension.json` + `scripts/sync-to-gemini.{sh,ps1}` mirrors `skill/` (+ `GEMINI.md`) into `~/.gemini/agents/dreamteam/`.
- **Codex** → an `AGENTS.md` entry + `scripts/sync-to-codex` mirrors `skill/` into `~/.agents/skills/dreamteam/` (the Codex skills layout the sync script targets).
- **CodeWhale** → `scripts/sync-to-codewhale` mirrors `skill/` into `~/.codewhale/skills/dreamteam/` (loaded via the `/skills` command); the global-instructions fallback is `~/.agents/AGENTS.md`.
- **OpenCode** → `scripts/sync-to-opencode.{sh,ps1}` mirrors `SKILL.md` + `references/` into `~/.config/opencode/skills/dreamteam/` (OpenCode's native Agent-Skills home, loaded on-demand via the native `skill` tool). **No-sync shortcut:** OpenCode also natively reads `~/.claude/skills/<name>/SKILL.md`, so a dreamteam already installed via `install.sh` is auto-discovered there with no extra step. Global-instructions fallback: `~/.config/opencode/AGENTS.md` (or the shared root `AGENTS.md`, which OpenCode reads natively). The skill loader injects `SKILL.md` only; `references/*.md` are read on demand via the file `read` tool from the synced folder — the same on-disk mechanism the other non-Claude syncs already rely on.
- **Cursor** → `scripts/sync-to-cursor.{sh,ps1}` mirrors `SKILL.md` + `references/` into `~/.cursor/skills/dreamteam/` (Cursor's native Agent-Skills home — the agentskills.io open standard, so the `name` + `description` frontmatter is Claude-compatible; skills are auto-matched on `description`, with `references/` loaded on demand). **No-sync shortcut:** Cursor also reads `~/.claude/skills/` (and `~/.agents/skills/`) for compatibility, so a dreamteam already installed via `install.sh` is auto-discovered there with no extra step. No AGENTS.md downgrade needed; a project-root `AGENTS.md` is read natively — Cursor's docs document no *global* AGENTS.md file (global prose preferences are its UI-managed User Rules).

## Graph tool (`graphify`) — engine-level, not per-OS
The optional AST code-graph (`--graph on|off|auto`; `loop.md` §Graph, `SKILL.md` Composes) integrates at the **engine level via portable Python**, **not** through any per-CLI / per-OS skill body — so `--graph` resolves **identically on Claude Code, Codex, Gemini, CodeWhale, OpenCode, and Cursor**, with no tool-name or dispatch mapping. graphify exposes three cross-platform integration surfaces:
- **CLI** — `graphify <repo>` builds, `graphify --update` refreshes (code-only = AST = free); the conductor shells out via each CLI's Bash / `run_shell_command` equivalent (see the Tool-name map).
- **MCP server** — `graphify --mcp` (`python -m graphify.serve graphify-out/graph.json`) exposes `query_graph` / `get_neighbors` / `shortest_path` / … so any MCP-capable producer or reviewer can query the live graph; register it in the host CLI's MCP settings.
- **git-hook** — `graphify hook install` adds a post-commit hook that re-runs AST extraction on changed files. Install it on the **main working tree only — never in producer worktrees** (`superpowers:using-git-worktrees`): a per-worktree hook would rebuild the graph on every isolated producer commit. (G1 in `loop.md` rides `integrate` on the main tree.)

Install is **uv/pipx, recommend-only** (`recommend.md`); the graph is **infra — never a gate, never a verdict** (`loop.md` §Graph). Absent / `--graph off` / oversized repo → skip silently, the run continues.

Environment / sandbox + worktree handling is inherited from the composed superpowers skills (`using-git-worktrees`, `finishing-a-development-branch`) — dreamteam must use those, not a hand-rolled `git checkout -b`.

`--platform` defaults to **auto**: detect the host by its config-dir marker — `~/.claude` → claude, `~/.gemini` → gemini, `~/.codewhale` → codewhale, `~/.config/opencode` (or an `opencode.json`) → opencode, `~/.cursor` → cursor, `~/.agents` (or an `AGENTS.md`) → codex; `--platform` overrides the guess. **Order matters:** OpenCode and Cursor both read `~/.agents`-family surfaces (OpenCode: `~/.agents`/`AGENTS.md` + `~/.claude/skills`; Cursor: `~/.agents/skills` + `~/.claude/skills` + project `AGENTS.md`), so their distinctive markers — `~/.config/opencode`, `~/.cursor` — are checked **before** the `~/.agents` → codex fallback.
